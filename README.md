# Industrial Copilot — Margin Engine

**An industrial copilot that computes distance to the failure boundary instead of
predicting the probability of failure.** Every number in every answer is
calculated, traced, and verified — never generated by a language model.

Built on the [UCI AI4I 2020 Predictive Maintenance Dataset](https://archive.ics.uci.edu/dataset/601/ai4i+2020+predictive+maintenance+dataset).

The question below is the brief's own example. Its premise is false, and the
system says so before answering. **This transcript is generated, not typed** —
`make verify` re-runs it and fails the build if a single figure drifts.

## Why this is different

The AI4I failure modes are **rules, not patterns**. We transcribed each from the
dataset documentation and scored it against the published labels on all 10,000
rows:

| Mode | Rule | Fires | Labelled | FP | FN |
|---|---|---:|---:|---:|---:|
| HDF | ΔT < 8.6 K **and** rpm < 1380 | 115 | 115 | **0** | **0** |
| PWF | torque·ω < 3500 W **or** > 9000 W | 95 | 95 | **0** | **0** |
| OSF | wear·torque > 11k/12k/13k (L/M/H) | 98 | 98 | **0** | **0** |

**287 of 339 failures are exactly explainable by arithmetic.** Answering *"why
did this fail?"* with a gradient-boosted probability converts a known quantity
into an estimate — and then cannot act on it.

A **margin** is a signed scalar in engineering units (`−1,433 min·N·m past the
overstrain limit`). Three properties follow:

- **It inverts** → the system *prescribes*: "reduce torque 4.2 N·m and every margin returns positive."
- **It's continuous** → the system *forecasts*: 579 healthy cycles come within 5% of failing, against 339 total failures. The binary label sees none of them.
- **It's associative** → the system *scales*: `min()` composes losslessly up a rollup tree.

### But a margin needs a boundary — and most failures don't have one

This is the strongest criticism of the approach, and it is correct. Only about
15–20% of real industrial failure modes have a discrete boundary. Bearing
spalling, heat-exchanger fouling, cavitation and chatter are continuous
degradation; forcing a threshold onto them manufactures a precision that isn't
there.

The answer is not to abandon margins — where a boundary genuinely exists, an
exact distance is *strictly better* than a probability, because it inverts into
a setpoint. The answer is to **say which kind of claim each answer is**:

| Regime | What the system is entitled to claim | AI4I | Failures |
|---|---|---|---:|
| **Exact** | a documented boundary exists; distance is arithmetic | HDF · PWF · OSF | 287 |
| **Statistical** | no crisp edge; an interval with a *coverage guarantee* | TWF | 46 |
| **Irreducible** | no predicate over any measured parameter — unknowable | RNF | 1 |

The split was already declared in `failure_modes.yaml` from the first commit;
the answer path simply never read its own knowledge base.

For the statistical regime the interval comes from **split conformal
prediction** — distribution-free (a wrong degradation model still yields a valid
interval) and finite-sample exact rather than asymptotic. Validated
leave-one-out on the 46 observed tool failures:

| α | Interval | Promised | **Achieved** |
|---|---|---|---|
| 0.10 | [200, 246] min | ≥ 90% | **91.3%** |
| 0.05 | [198, 253] min | ≥ 95% | **95.7%** |
| 0.01 | — | ≥ 99% | **refused — 46 samples cannot support it** |

The last row is the point. The 90% interval also brackets the documented
200–240 min window without ever reading it.

→ [copilot/regimes.py](copilot/regimes.py)

### Language models are bad at time series. We removed them from the numeric path.

Tokenization destroys numeric magnitude; context windows cannot hold a sensor
stream; arithmetic is approximated. Our answer is structural — **the model never
sees the time series.** It converts intent to a validated plan, and later phrases
a result. Everything between is deterministic arithmetic.

→ [docs/02-TIME-SERIES.md](docs/02-TIME-SERIES.md)

## Architecture

Four questions, asked in order. Each layer can stop the answer, and the final
response inherits the weakest link in its own chain.

```
┌──────────────────────────────────────────────────────────────────────────┐
│ L1  PLANT      PLC/SCADA · MES · Historian · MQTT · OPC-UA · CSV replay  │
└────────────────────────────────┬─────────────────────────────────────────┘
                                 │ raw messages
┌────────────────────────────────▼─────────────────────────────────────────┐
│ L2  INTAKE          ── is this message even usable? ──                    │
│     event time vs ingestion time · dedupe (at-least-once IS the contract) │
│     watermark + lateness bound · gap detection · clock-skew rejection     │
│                                            copilot/intake.py             │
├───────────────────────────────────────────────────────────────────────────┤
│     OBSERVER        ── is the signal real? ──                             │
│     per-channel Kalman · chi-square on innovation energy → stuck sensor   │
│     CUSUM (Siegmund ARL) → drift · parity relations across channels       │
│     INSTRUMENT fault vs PROCESS fault · NAMUR NE 107 status               │
│     noise identified from the signal, never declared    copilot/observer.py│
└────────────────────────────────┬─────────────────────────────────────────┘
                                 │ trusted values + uncertainty
┌────────────────────────────────▼─────────────────────────────────────────┐
│ L3  PHYSICS         ── how far from the boundary? ──                      │
│     dimensional typing · derived quantities (ΔT, power, overstrain)       │
│     MARGINS — signed scalars, stateless, 0.22 µs                          │
│     REGIME: exact │ statistical (conformal) │ irreducible                 │
│                          copilot/physics.py · regimes.py · process_model.py│
└────────────────────────────────┬─────────────────────────────────────────┘
                                 │ margins + evidence
┌────────────────────────────────▼─────────────────────────────────────────┐
│ L4  REASONING       ── is the number right, and the claim supported? ──   │
│     Analysis IR: validate · compile · execute  →  Evidence bundle         │
│     premise verification · permutation null on rankings · collinearity    │
│     narrator writes {{slots}} → fail-closed verifier rejects bare digits  │
│                                     copilot/ir.py · ops/ · verify.py      │
└────────────────────────────────┬─────────────────────────────────────────┘
                                 │ verified answer
┌────────────────────────────────▼─────────────────────────────────────────┐
│ L5  ACTION   Envelope explorer · Fleet · Reliability · Chat · [writeback] │
└──────────────────────────────────────────────────────────────────────────┘
       Data flows up.  Decisions flow down.  [bracketed] = roadmap.
```

The process definition is **data, not code** — `failure_modes.yaml` drives
`physics.py`, so onboarding a different plant is a file, not a build. A test
runs a hydraulic press with different metrics and per-variant limits through
identical code, and `scripts/onboard.py` discovers a config from a plant's
history (recovering the documented AI4I thresholds to 0.00–0.58% with nothing
upstream reading the docs).

### Request lifecycle

```
question → resolver(session state) → ROUTER ─┬─ plan cache       ~0 ms
                                             ├─ grammar planner  ~1 ms
                                             ├─ verified exemplars ~1 ms  ← learns
                                             └─ LLM planner    ~400 ms
   → Analysis Plan (JSON)
   → schema validator ──(invalid)──► repair ×1 ──► else refuse
   → typed executor → DuckDB                              <10 ms
   → evidence bundle (slots + units + provenance)
   → narrator (writes {{slot}} refs, never digits)
   → PCN verifier ──(bare numeral)──► REJECT ──► regenerate
   → verified answer + evidence + replay handle
```

### The four gates

| Gate | Doubt | Mechanism |
|---|---|---|
| 1 | Is the question's **premise** true? | Premise verification before answering |
| 2 | Is the **instrument** honest? | Physics invariant monitors |
| 3 | Is the **rule** still valid? | KB calibration monitor |
| 4 | Is every **number** sourced? | Proof-Carrying Numbers (fail-closed) |

A **0.4 K thermocouple drift makes heat-dissipation alerts drop 54%.** A
conventional copilot reports "failures down 54% — good month" while the plant
goes blind. Gate 2 separates the two by CONTRAST rather than magnitude: a
thermocouple drift moves ΔT (z=+2.8) and leaves speed alone (z=−1.3), while a
genuine slowdown moves speed hard (z=−46.4). Both z-scores are corrected for
serial correlation — the naive standard error assumes independent samples and
overstates an autocorrelated channel about fourteenfold. → [docs/06-RELIABILITY.md](docs/06-RELIABILITY.md)

## Setup

**Requirements:** Python 3.11+ (tested on 3.14), ~200 MB disk. No GPU. **No API key required.**

```bash
git clone <repo-url> && cd industrial-copilot
python3 -m venv .venv && source .venv/bin/activate
pip install -e .
```

Place the dataset at `data/ai4i2020.csv` (download from
[UCI](https://archive.ics.uci.edu/dataset/601/ai4i+2020+predictive+maintenance+dataset)),
then:

```bash
make build          # CSV → DuckDB with physics + margins
make verify         # reproduce every figure in docs/01-DATASET.md
make demo           # scripted walkthrough
```

## Running

```bash
make demo      # scripted walkthrough of all four acceptance criteria
make chat      # interactive terminal copilot
make ask Q="why did cycle 9016 fail?"
make serve     # API, chat console, envelope explorer and fleet view on :8000
               #   /             ask, with evidence drill-down on every answer
               #   /fleet/view   every machine ranked on one axis of risk
               #   /explorer     the operating envelope, draggable
               #   /reliability  Gates 2 and 3, live and interactive
make stream    # replay the fleet with live lead-time alerts
```

**Evidence you can re-run.** Every number in this README comes from one of these:

```bash
make verify    # every documented figure, incl. the README's own example
make eval      # golden suite, 27 cases; hard gates fail the build
make coverage  # risk-coverage: how much we answer AND how sound it is
make test      # 388 unit and adversarial tests
make onboard   # discover a process definition from raw history, then audit it
make discover  # re-derive the documented thresholds from data alone
make bench     # margin throughput benchmark
make docker    # build the deployment image (non-root, read-only)
```

`make onboard` is the one worth running if you only run one. It takes the raw
CSV, profiles every channel with no configuration, detects target leakage
(AI4I ships the mode flags beside the label), discovers conjunctive failure
rules, and grades each one — then audits the result against the documented
thresholds it never saw.

## Configuration

All settings live in `copilot/config.py`; nothing else reads the environment.

| Variable | Default | Purpose |
|---|---|---|
| `COPILOT_CSV` | `data/ai4i2020.csv` | dataset path |
| `COPILOT_DB` | `data/warehouse.duckdb` | warehouse path |
| `COPILOT_PROVIDER` | `deterministic` | `deterministic` \| `anthropic` \| `cerebras` \| `ollama` |
| `ANTHROPIC_API_KEY` | — | enables the Claude planner/narrator |
| `CEREBRAS_API_KEY` | — | free tier: 30 RPM, 60k TPM, 1M tok/day |
| `COPILOT_PLANNER_MODEL` | `claude-haiku-4-5` | planner model |
| `COPILOT_LLM_NARRATION` | `true` | disable for template narration |

**With no provider configured the system is fully functional and fully
evaluable.** The deterministic grammar planner and template narrator cover the
acceptance criteria; adding a key improves phrasing, not correctness. Graceful
degradation to *less fluent* — never to *wrong* — is a deliberate systems
property.

## Performance

Three figures for three different things — conflating them would overstate the case:

| Measurement | Result |
|---|---|
| Raw margin arithmetic, vectorised | **419 M samples/sec/core** |
| Raw margin arithmetic, per event | **0.22 µs** → 4.6 M/sec/core |
| `evaluate()` returning a margin object | **1.09 µs** → 918 k/sec/core |
| Full stream scorer: robust track + alerting | **~14 µs** → ~72 k/sec/core |
| Requirement, 2,000-machine site @ 1 Hz | 2,000 events/sec |
| **Headroom on one core (full scorer)** | **~36×** |
| Query execution | < 10 ms |

Speed is not the result of optimisation — **there is no model to run at inference
time.** Intelligence lives in the knowledge base, built offline; online is
arithmetic.

### The fine-tuning bonus, and why it is not in the product

The brief invites fine-tuning as a bonus, so we did it properly: Qwen3-1.7B
distilled on 1,079 question→plan pairs with Unsloth, exported to GGUF, and
benchmarked **locally on the deployment hardware** rather than on the training
GPU — `scripts/bench_planner_local.py` re-derives the identical held-out split
and runs the exported model through Ollama.

It lost, and not narrowly:

| | Distilled 1.7B | Grammar tier |
|---|---:|---:|
| Coverage / exact match | **14.2%** | **98.4%** |
| Latency p50 | 719 ms | **3 ms** |

The cause is diagnosable rather than mysterious: the compact plan notation is
positional (`op\|cohorts\|metrics\|…`), so the model has to count pipe
separators, which is close to the worst thing to ask of a transformer. Its
errors were almost all right-content-wrong-slot. Grammar-constrained decoding
would likely fix it — and would be days of work to improve a component the
system does not need, since 93% of questions never reach a model tier at all.

**So the finding ships and the model does not.** The brief says there is no
credit for using the best LLM and asks for a focus on latency and hallucination;
this is what that looks like when you measure instead of assume. The notebook
runs end to end (`make notebook`) so the result is reproducible, and the
benchmark stays in the repo so the claim is checkable.

## Assumptions (summary)

AI4I has **no timestamps** and **no machine identity**. We overlay a 2-minute
takt from a fixed epoch, and a virtual fleet assigned round-robin within quality
variant. **Every synthetic dimension is tagged `SYNTHETIC` in the semantic layer,
and any answer relying on one says so in the response.**

Full list, including the load-bearing assumption that documented thresholds are
given: [docs/12-ASSUMPTIONS.md](docs/12-ASSUMPTIONS.md).

## Intellectual honesty

Almost every component here is **established practice, not invention** — and
that is the point. A commissioned adversarial technical review found most of the
design to be rediscovery, and it was right:

| Component | Prior art | Novel? |
|---|---|---|
| Margin, and `min()` composition | First-passage-time RUL (1990s); `min()` up a hierarchy is Fault Tree Analysis, Bell Labs 1960s | **No** |
| Observer-based FDI | Isermann, Gertler (1980s). Kalman 1960, CUSUM 1954 | **No** |
| NAMUR NE 107 status | Standardised 2006, universal in process industries | **No** |
| Abstention via interval arithmetic | Moore 1966; selective prediction in NLP | **No** |
| Rule induction from history | FOIL (1990), RIPPER (1995), CN2 separate-and-conquer | **No** |
| Semantic layer over raw schema | Cortex Analyst: 57% → 78% on BIRD | **No** |
| Slot-bound numeric verification | [Proof-Carrying Numbers, arXiv:2509.06902](https://arxiv.org/abs/2509.06902) | **Partial** |
| Premise verification on time-series questions | NLP false-presupposition work; rare in this domain | **Partial** |

**Two corrections this review forced**, recorded because they were claims made
here first and they were wrong:

- An earlier version of this README claimed sensor/process discrimination had
  no prior art. **C3 AI ships it** as "native data veracity algorithms," sensor
  health versus system reliability, with a published 99% false-alert reduction.
  The distinction is real and valuable; it is not ours.
- An earlier design note called `power = torque × ω` an analytical redundancy
  relation. Power is *derived* from those two channels, so its residual is
  identically zero and it carries no information. Only the two independently
  instrumented thermocouples provide genuine redundancy here.

What is left, and what we would actually defend:

1. **The regime split.** Saying, per answer, whether a number is exact,
   statistical with a stated coverage guarantee, or unknowable. No product
   surveyed does the third.
2. **The coverage/soundness pair, published together.** AssetOpsBench reports
   completion without correctness; AgentAbstain measures refusal in isolation.
3. **The composition**, and the discipline that every constant is derived from
   a declared error budget rather than chosen.

**This is not a better product than Siemens Senseye or Cognite.** They own the
OT connector moat, real sensor modalities, and years of deployment learning. It
is a better *answer engine* on this dataset, on the axes the brief names, built
against the documented reason most industrial AI never leaves pilot: not
algorithm performance, but data quality, integration, and trust.
